# Яндекс Календарь

Интеграция отправляет встречи из «Голоса» в выбранный пользователем календарь Яндекса по CalDAV. Каждый пользователь подключает свой аккаунт; пароль приложения хранится на сервере в зашифрованном виде. Задачи и напоминания остаются локальными. Сервис — источник правды: ручные изменения связанных событий в Яндексе перезаписываются локальным состоянием. Изменения из Яндекса не импортируются. Сохранение встречи и успешный ответ ассистента подтверждают локальное действие; доставку в Яндекс подтверждает отдельный статус синхронизации.

## Подключение

1. Выберите существующий календарь или создайте отдельный вручную в Яндекс Календаре. Интеграция не создаёт календарь автоматически.
2. В Яндекс ID создайте пароль приложения с доступом к календарю: https://yandex.ru/support/id/ru/authorization/app-passwords . Используйте пароль приложения, а не обычный пароль аккаунта.
3. Откройте «Настройки → Яндекс Календарь» по HTTPS (для разработки допустим localhost). Введите логин и пароль приложения, нажмите «Проверить доступ». Пароль сразу очищается из формы, включая ошибочные попытки.
4. Выберите найденный календарь с правом записи и явно нажмите «Подключить выбранный календарь». До этого шага встречи не отправляются.
5. Нажмите «Синхронизировать встречи», чтобы отправить все текущие встречи, включая созданные до подключения. Новые встречи и последующие локальные изменения отправляются автоматически.

Адрес сервера фиксирован: `https://caldav.yandex.ru`. Пользователь не вводит произвольный URL сервера. Учётные данные не сохраняются в cookie, localStorage или URL. После перезагрузки на этапе выбора календаря повторите проверку доступа. Для отозванного пароля создайте новый пароль приложения и подключите календарь заново в настройках.

## Эксплуатация

Сохраните `YANDEX_TOKEN_KEY` в Kubernetes Secret `secrets` через используемую систему управления секретами. Сгенерировать ключ Fernet: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Ключ требуется только сервису yandex-calendar и должен быть стабильным при перезапусках: его потеря требует повторного подключения пользователей. Никогда не коммитьте ключи и пароли. Необязательная ссылка Secret позволяет установить сервис без включения интеграции. `YANDEX_CALENDAR_URL=http://yandex-calendar:8000` задан в ConfigMap.

Чтобы добавить заранее сгенерированный ключ в существующий Secret, замените `ВАШ_КЛЮЧ_FERNET` своим значением и выполните:

```bash
kubectl -n voice-assistant patch secret secrets --type=merge -p '{"stringData":{"YANDEX_TOKEN_KEY":"ВАШ_КЛЮЧ_FERNET"}}'
```

Команда сохраняет остальные поля Secret, но заменяет `YANDEX_TOKEN_KEY`, если он уже существует. Замена ключа делает ранее сохранённые пароли недоступными для расшифровки и требует повторного подключения пользователей. После изменения Secret перезапустите сервис:

```bash
kubectl -n voice-assistant rollout restart deployment/yandex-calendar
```

Порядок обновления: additive-миграция через auth → core → yandex-calendar → frontend. Сначала обновите ConfigMap и Secret. При откате сохраните новые таблицы и данные; не запускайте разрушительные downgrade-миграции. Автоматическая CI-сборка обнаруживает `services/yandex-calendar/app/build.sh`. Этот скрипт выполняет push и rollout, его нельзя использовать как локальную проверку. Сервис запускает HTTP и RabbitMQ worker через FastAPI lifespan. Образ собирается только из `services/yandex-calendar/app/`.

## Синхронизация по данным сервиса

В настройках подключённого календаря доступна кнопка «Синхронизировать встречи». Она создаёт задания для всех встреч пользователя, включая старые и повторяющиеся. Существующие связанные события восстанавливаются по полному локальному снимку, отсутствующие — создаются с сохранённым UID. Для отменённых и удалённых локально встреч с известной связью обеспечивается отсутствие события в Яндексе. Посторонние события, которые сервис не создавал и с которыми у него нет связи, не читаются массово и не изменяются.

Перенос сразу записывает итоговое локальное состояние поверх ручных изменений в Яндексе. Удаление удаляет связанный ресурс, даже если он изменён вручную; если он уже отсутствует, это успех. Промежуточное восстановление перед удалением не требуется. Поиск по сохранённому UID восстанавливает адрес ресурса, если он изменился внутри выбранного календаря. Отдельные повторения по-прежнему входят в один ресурс серии.

Кнопка вызывает `POST /api/v1/integrations/yandex-calendar/sync` и получает `{ "queued": N }`: это подтверждение постановки в очередь, а не завершения синхронизации. Core сохраняет неизменяемые снимки и outbox в одной транзакции. Отправка идёт через существующую очередь `yandex_calendar`; результат приходит через callback core и WebSocket. Повторное нажатие не дублирует уже ожидающее задание для той же локальной версии. Новая сверка уже синхронизированной встречи получает новую ревизию синхронизации, не меняя версию локальной записи. Поля `version` и `synced_version` статуса относятся к этим ревизиям. Изменение схемы БД для этой модели не требуется.

Старые `conflict` / `missing` не блокируют новые задания: кнопка или новое локальное изменение восстанавливает связь. Завершённые неуспешные операции заменяются новым полным снимком; ещё выполняющаяся предыдущая операция должна завершиться первой. Старый callback не подтверждает новую ревизию, а поздняя доставка не откатывает более новую запись в Яндексе. Сохранённая идентичность не меняется из-за технической ошибки создания.

Проблемы синхронизации видны в настройках, включая ошибки удаления локальных встреч. В карточках статус появляется только при подключённом календаре. После загрузки и WebSocket reconnect состояние восстанавливается через REST. Технические ошибки можно повторить. Отключение удаляет credentials, останавливает старые задания и сохраняет события Яндекса. Новое подключение имеет отдельное поколение; кнопка отправляет встречи в выбранный новый календарь, не очищая предыдущий.

## Проверка без раскрытия секретов

Unit/SSR тесты и mock frontend не обращаются к Яндексу. Для отдельной явно разрешённой live-проверки подготовьте файл вне репозитория с правами `0600`, JSON-объектом `{ "username": "...", "password": "...", "calendar_id": "..." }` и передайте только путь через `YANDEX_TEST_CREDENTIALS_FILE`. Не выводите содержимое файла в терминал, логи, чат или отчёт. Не сохраняйте его среди артефактов тестов. Live-проверка требует отдельного тестового календаря и явного разрешения на реальные записи; обычные тесты не выполняют реальные изменения.

```sh
cd services/yandex-calendar/app
uv run pytest -q
# Только с отдельным тестовым календарём и приватным файлом:
YANDEX_TEST_CREDENTIALS_FILE=/private/tmp/yandex-test.json uv run pytest tests/test_yandex_live.py -q -s
```

CalDAV может вернуть другой адрес созданного ресурса. Сервис проверяет адрес из ответа и при необходимости ищет собственный UID в выбранном календаре. Он сохраняет полученный адрес, нормализованное содержимое и ETag. Яндекс удаляет произвольные `X-` поля: восстановление после потерянного ответа опирается на сохранённое намерение и проверку содержимого, а не на сохранность такого маркера. Повторная активация ранее удалённой встречи получает новый UID.

После успешного PUT достаточно прочитать событие с ожидаемым UID и получить его ETag: различия представления iCalendar не вызывают конфликт. Перед изменением или удалением сервис читает связанное событие, проверяет UID и использует его свежий ETag в `If-Match`. Изменившийся ETag означает внешнее расхождение, которое перезаписывается локальным состоянием. Если ресурс меняется между чтением и записью (`412`), операция повторяется с задержкой и новым чтением. Полное сравнение содержимого применяется только при восстановлении после неоднозначного ответа, чтобы определить, была ли выполнена операция.

Живая проверка условных записей: устаревший настоящий ETag в `If-Match` отклоняется с `412`. Однако Яндекс игнорирует `If-None-Match: *` и может заменить существующий ресурс. Поэтому атомарную гарантию «создать только при отсутствии» сервер не предоставляет. Первое создание использует уникальный UID, предварительное чтение и сериализацию в БД. После неоднозначного исхода создания повторная доставка выполняет только чтение и поиск по UID; повторный PUT запрещён. Если подтвердить создание не удалось, ограниченные повторы завершаются ошибкой в core. Ручной технический повтор продолжает безопасную сверку; он не создаёт ресурс заново. Это ограничение провайдера по сравнению с исходным планом.

Описание часового пояса включает историческую базу с 1970 года (или раньше для более старой встречи): Яндекс неверно разбирает определения, начинающиеся только в будущем. Библиотека генерирует переходы; полный ответ сохраняется для восстановления после неоднозначного результата, а ETag — для обнаружения последующих внешних изменений.

## Результаты проверки реализации

Исходящие запросы к Яндексу ограничены общим для процесса лимитом 5 RPS: между запросами выдерживается минимум 200 мс, без накопления burst-квоты. Лимит действует на обнаружение календарей, чтение, запись, удаление и повторные запросы обоих HTTP-транспортов. Обработка `Retry-After` сохраняется. При нескольких процессах или репликах каждый имеет отдельный лимит; текущий Deployment использует одну реплику.

Новая модель проверена автотестами с подменённым CalDAV: полная сверка старых встреч, восстановление внешних изменений и удалений, перенос и удаление после ручной правки, неизменность посторонних событий, повторная доставка, потерянные ответы, последовательность ревизий и изоляция пользователей. Пайплайн domain/outbox → worker → CalDAV → core → Event проверен целиком. Последний backend-прогон: 135 passed, 8 skipped; пропуски требуют внешних зависимостей или явного live-запуска. Все 23 frontend-теста и production-сборка проходят. В браузере с подменённым API проверены кнопка, POST-запрос и сообщение о постановке встреч в очередь.

В предыдущей версии 25 октября 2026 года live-тест подтвердил совместимость Яндекса с созданием, переносом, напоминанием, сериями через DST, отдельными повторениями и удалением, а также ограничения условных запросов. Новая модель перезаписи и полной сверки повторно на реальном аккаунте не запускалась: приватные тестовые credentials удалены после предыдущего прогона. Opt-in live-тест обновлён под новое поведение.

Образ Docker и развёртывание в Kubernetes не выполнялись. Полная проверка с настоящими PostgreSQL/RabbitMQ требует соответствующего тестового окружения; доставка проверена с подменёнными транспортами и транзакционной БД. Для включения интеграции в окружении нужны миграция, сервис и Secret с `YANDEX_TOKEN_KEY`; тестовые credentials в репозиторий не включены.

Живая проверка выявила ограничение Яндекса: экспортируемое время округляется до минуты. Встречи с ненулевыми секундами или микросекундами сохраняются локально, но получают ошибку `calendar_precision_unsupported` вместо отправки с потерей точности. Технический повтор такую ошибку не исправляет; изменение времени до целой минуты создаёт новое задание, которое может продолжить отправку.
