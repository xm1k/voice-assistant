# Голос v2 — данные и запросы пользователя

Личный помощник, который превращает сообщения и голос в задачи, встречи и напоминания. Он находит сохранённые записи, отвечает на вопросы о расписании и меняет данные по запросу пользователя.

**Модель понимает запрос и предлагает действие. Core — основной сервис приложения — проверяет его и сохраняет результат в PostgreSQL.** Текст «готово» сам по себе не означает, что данные изменились.

[Запуск и настройка](README.md) · [Архитектура](ARCHITECTURE.md) · [Точный контракт модели](docs/llm-service.md)

## Что можно попросить

| Пример запроса | Что делает система |
|---|---|
| «Создай задачу: подготовить отчёт к пятнице» | Создаёт задачу со сроком |
| «Завтра в 15:00 встреча с Анной на час» | Создаёт встречу с началом и окончанием |
| «Напомни завтра в 09:00 оплатить интернет» | Создаёт напоминание на указанное время |
| «Какие встречи у меня завтра?» | Выбирает встречи за день |
| «Найди задачи про ремонт» | Ищет по словам и смыслу |
| «Сколько активных задач на этой неделе?» | Считает записи по фильтрам |
| «Найди свободный час завтра с 9 до 18» | Вычисляет свободные интервалы |
| «Перенеси завтрашнюю встречу с Анной на 17:00, на час» | Находит запись, получает её версию и меняет время |
| «Удали напоминание об оплате интернета» | Находит запись и выполняет удаление |

Это примеры намерений, а не фиксированные команды. Если для действия не хватает данных или выбор неоднозначен, помощник может задать уточняющий вопрос. «Завтра» и другие относительные даты определяются по времени сообщения и часовому поясу пользователя.

## Как сообщение становится результатом

![Шесть этапов: сообщение, сохранение задания, контекст модели, решение, проверка и сохранение, ответ.](docs/assets/request-flow.gif)

[Статичная версия схемы](docs/assets/request-flow.png)

1. **Ввод.** Пользователь отправляет текст или аудио. Голос сначала распознаётся в текст и затем идёт по тому же пути; браузер не отправляет транскрипцию повторно.
2. **Регистрация.** Core сохраняет сообщение, задание (`job`) и запись на отправку в очередь (`outbox`) одной транзакцией. Ответ HTTP 202 означает, что запрос принят в обработку.
3. **Контекст.** Через RabbitMQ задание получает assistant-worker. Он запрашивает у core последние 30 релевантных сообщений, незавершённое уточнение, часовой пояс и время запроса.
4. **Решение.** Модель возвращает структурированный ответ: уточнить, запросить данные или подготовить итоговое действие. При поиске найденные данные возвращаются модели для следующего шага.
5. **Проверка и запись.** Core предварительно проверяет решение без сохранения. После доставки результата он проверяет его повторно и применяет команды одной транзакцией: весь пакет либо сохраняется, либо откатывается.
6. **Ответ.** В историю попадают итог и карточки записей; интерфейс получает события по WebSocket. После переподключения состояние восстанавливается через HTTP. Подтверждение изменения строится из сохранённых данных.

### Маршрут по сервисам

#### Запрос между блоками сервисов

![Анимация переноса встречи: блоки сервисов остаются на месте, синий маркер движется от отправителя к получателю; подпись поясняет каждый запрос и ответ.](docs/assets/service-blocks.gif)

[Статичный кадр — открыть в полном размере](docs/assets/service-blocks.png)

Здесь показан конкретный запрос: **«Перенеси завтрашнюю встречу с Анной на 17:00, на час»**. Сервисы остаются на своих местах. Синий блок отправляет запрос, зелёный принимает, движущийся маркер показывает направление. Внизу написано, **что передаётся и зачем**. Каждый шаг длится около **5 секунд**, полный цикл — 2 минуты 10 секунд.

Схема показывает успешный сценарий с точной выборкой встреч. Для поиска по смыслу RAG дополнительно обращается к векторам PostgreSQL; уточнения, ошибки и повторы здесь опущены. Промежуточный HTTP 202 и технические подтверждения также не показаны.

#### Последовательность обмена

![Маршрут запроса: браузер → gateway → core, проверка сессии через auth, сохранение в PostgreSQL, доставка через RabbitMQ в assistant-worker, обращения к LLM и RAG, проверка и сохранение в core, ответ через gateway.](docs/assets/service-route.gif)

[Статичная версия — открыть в полном размере](docs/assets/service-route.png)

Схема читается сверху вниз: каждая стрелка показывает отправителя и получателя. `gateway` принимает внешний трафик, `auth` проверяет сессию, `core` управляет данными, а `RabbitMQ` доставляет задания и решения. `assistant-worker` вызывает LLM и при необходимости обращается к `RAG` за данными. Процессы **publisher** и **results** работают внутри core.

Ветка `RAG` выполняется только при запросе данных. Точные выборки делает core; при смысловом поиске RAG дополнительно читает актуальные векторы из PostgreSQL. Результаты возвращаются worker и затем модели. Схема показывает успешный проход; уточнения, исправления и повторные запросы могут добавлять шаги.

**Для голоса перед этим маршрутом добавляется распознавание:**

```text
Браузер → gateway → voice
                    ├─ auth: проверка сессии
                    ├─ общее хранилище: аудиофайл
                    └─ core: регистрация задания
                         → RabbitMQ → transcription-worker
                                      ├─ чтение аудио → Whisper / внешний STT
                                      └─ текст → core → задание assistant-worker
```

После распознавания core создаёт текстовое сообщение и задание для assistant-worker. Дальше выполняется тот же путь обработки текста; повторной отправки из браузера нет.

### Три варианта решения модели

| Ветка | Когда нужна | Результат |
|---|---|---|
| `clarify` — уточнить | Не хватает параметров | Вопрос пользователю и сохранённый контекст для продолжения |
| `query` — получить данные | Нужны записи, количество или свободное время | Запрос через RAG/core, затем новое обращение к модели |
| `ready` — завершить | Можно ответить или выполнить действие | Обычный ответ без изменений либо проверенный пакет команд |

Например: «Создай напоминание оплатить интернет» → «Когда напомнить?» → «Завтра в девять утра» → создание напоминания. Сохранённый контекст уточнения связывает эти сообщения.

## Какие данные хранит приложение

| Данные | Содержимое и назначение |
|---|---|
| Задача (`task`) | Название, заметки, статус, необязательный срок |
| Встреча (`meeting`) | Название, начало и окончание, часовой пояс; окончание обязательно позже начала |
| Напоминание (`reminder`) | Название и обязательное время напоминания |
| Повторения | Ежедневное, еженедельное или ежемесячное правило; исключения для отдельных повторений |
| Диалог | Сообщения, карточки результатов и контекст незавершённого уточнения |
| Обработка | Задания, их результаты и ошибки, события, уведомления и очередь отправки |
| Поисковый индекс | Векторное представление записи, её версия и название embedding-модели |

У основной записи есть **владелец `user_id`, идентификатор `id` и версия `version`**. Версия позволяет обнаружить изменение записи между поиском и сохранением. Статусы записей: активна, завершена, отменена. Удаление основной записи логическое: запись помечается удалённой и исключается из обычной работы, а не немедленно стирается из БД.

Учётные записи и сессии находятся в базе `golos_auth`, предметные данные — в `golos_domain`. Аудио временно хранится в общем файловом хранилище для распознавания; предусмотрены удаление после обработки и фоновая очистка. Очистка чата сбрасывает контекст диалога и отменяет применение старых ответов; это не команда удаления задач и встреч.

## Как работает поиск

![Поиск: запрос модели, фильтры пользователя, точная выборка или поиск по словам и смыслу, актуальные записи, ответ.](docs/assets/data-search.gif)

[Статичная версия схемы](docs/assets/data-search.png)

**Точные вопросы** — «что завтра», «сколько задач», «ближайшая встреча», «когда свободен» — обрабатываются типизированными запросами. Core применяет владельца, тип записи, статус и период, учитывает повторения. Для списка и подсчёта не требуется смысловое сходство с фразой пользователя.

**Поиск по тексту и смыслу** использует RAG — сервис получения данных для модели:

1. Core формирует допустимый набор записей с учётом пользователя и фильтров.
2. Текстовый поиск оценивает совпадения слов в названии и заметках. Семантический поиск сравнивает векторы запроса и записей, созданные моделью E5.
3. RAG объединяет два рейтинга и возвращает ограниченный список. Для векторного поиска подходят только индексы текущей версии записи и используемой модели.
4. Модель получает найденные записи и формирует ответ. Ссылки в ответе проверяются по реально полученным результатам.

Индекс обновляется в фоне и может отставать от записи. При недоступности семантического поиска предусмотрен поиск по тексту; совпадения по смыслу при этом могут не найтись. Источник истины — записи PostgreSQL, а не поисковые векторы.

## Как изменения защищены от ошибок

- **Модель не выполняет SQL.** Она предлагает команды `create`, `update`, `delete`; права и бизнес-правила проверяет core. Пользователь для поиска берётся из контекста задания, а не из ответа модели.
- **Перед изменением нужна актуальная запись.** Для обновления и удаления используются `id` и `version`, полученные запросом данных. Чужая запись недоступна даже при известном идентификаторе.
- **Проверка не равна сохранению.** Предварительная проверка выполняется с откатом и не резервирует запись. Конфликт при окончательном сохранении откатывает пакет и возвращает ошибку.
- **Повторы обработки контролируются.** Повторная доставка уже завершённого результата не применяет команды ещё раз. Это не означает дедупликацию двух отдельно отправленных одинаковых просьб.
- **Серия и отдельное повторение различаются.** Изменение всей серии использует `scope=series`, одного повторения — `scope=occurrence` и его точное время.
- **Ошибки исправляются ограниченно.** Неверный JSON, параметры и версии возвращаются модели для исправления. На один цикл отводится до восьми обращений к LLM; запросы данных тоже расходуют этот лимит. При неустранимой ошибке пользователь получает сообщение без ложного подтверждения.

## Что передаётся моделям

Выбранный LLM-провайдер получает контекст диалога, время и часовой пояс, результаты запрошенных выборок и ошибки проверки для исправления. **В этих данных могут быть тексты личных задач, встреч и заметок.** Вся база не передаётся целиком в каждом запросе, но приложение нельзя считать полностью локальным при выборе внешнего провайдера.

Распознавание речи настраивается отдельно: локальный Whisper обрабатывает аудио в инфраструктуре приложения; внешний STT-провайдер получает аудиофайл. Модель E5 строит поисковые векторы в сервисе приложения. Выбор LLM, STT и их настройки описаны в [основном README](README.md#модели-и-конфигурация).
