# Яндекс Календарь

Интеграция отправляет встречи из «Голоса» в выбранный пользователем календарь Яндекса по CalDAV. Каждый пользователь подключает свой аккаунт; пароль приложения хранится на сервере в зашифрованном виде. Задачи и напоминания остаются локальными. Изменения в Яндексе не импортируются. Сохранение встречи и успешный ответ ассистента подтверждают локальное действие; доставку в Яндекс подтверждает отдельный статус синхронизации.

## Подключение

1. Выберите существующий календарь или создайте отдельный вручную в Яндекс Календаре. Интеграция не создаёт календарь автоматически.
2. В Яндекс ID создайте пароль приложения с доступом к календарю: https://yandex.ru/support/id/ru/authorization/app-passwords . Используйте пароль приложения, а не обычный пароль аккаунта.
3. Откройте «Настройки → Яндекс Календарь» по HTTPS (для разработки допустим localhost). Введите логин и пароль приложения, нажмите «Проверить доступ». Пароль сразу очищается из формы, включая ошибочные попытки.
4. Выберите найденный календарь с правом записи и явно нажмите «Подключить выбранный календарь». До этого шага встречи не отправляются.

Адрес сервера фиксирован: `https://caldav.yandex.ru`. Пользователь не вводит произвольный URL сервера. Учётные данные не сохраняются в cookie, localStorage или URL. После перезагрузки на этапе выбора календаря повторите проверку доступа. Для отозванного пароля создайте новый пароль приложения и подключите календарь заново в настройках.

## Эксплуатация

Сохраните `YANDEX_TOKEN_KEY` в Kubernetes Secret `secrets` через используемую систему управления секретами. Сгенерировать ключ Fernet: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Ключ требуется только сервису yandex-calendar и должен быть стабильным при перезапусках: его потеря требует повторного подключения пользователей. Никогда не коммитьте ключи и пароли. Необязательная ссылка Secret позволяет установить сервис без включения интеграции. `YANDEX_CALENDAR_URL=http://yandex-calendar:8000` задан в ConfigMap.

Порядок обновления: additive-миграция через auth → core → yandex-calendar → frontend. Сначала обновите ConfigMap и Secret. При откате сохраните новые таблицы и данные; не запускайте разрушительные downgrade-миграции. Автоматическая CI-сборка обнаруживает `services/yandex-calendar/app/build.sh`; общий `shared/build.sh` также включает образ. Эти скрипты выполняют push и rollout, их нельзя использовать как локальную проверку. Сервис запускает HTTP и RabbitMQ worker через FastAPI lifespan. Docker runtime объединяет shared backend и overlay сервиса.

Проблемы синхронизации видны глобально, в том числе для удалённых локальных встреч и отозванных учётных данных. После WebSocket reconnect интерфейс получает актуальный REST-статус. Старые встречи без привязки показываются как «Только в Голосе». Технические ошибки `failed` / `delivery_exhausted` можно повторить. Конфликт с внешними изменениями или удалённое в Яндексе событие блокируют эту привязку навсегда: технический повтор не перезаписывает и не пересоздаёт такое событие. Отключение останавливает доставку и не означает удаление локальных встреч.

## Проверка без раскрытия секретов

Unit/SSR тесты и mock frontend не обращаются к Яндексу. Для отдельной явно разрешённой live-проверки подготовьте файл вне репозитория с правами `0600`, JSON-объектом `{ "username": "...", "password": "...", "calendar_id": "..." }` и передайте только путь через `YANDEX_TEST_CREDENTIALS_FILE`. Не выводите содержимое файла в терминал, логи, чат или отчёт. Не сохраняйте его среди артефактов тестов. Live-проверка требует отдельного тестового календаря и явного разрешения на реальные записи; обычные тесты не выполняют реальные изменения.

```sh
shared/.venv/bin/python -m pytest shared/tests_v2 -q
# Только с отдельным тестовым календарём и приватным файлом:
YANDEX_TEST_CREDENTIALS_FILE=/private/tmp/yandex-test.json shared/.venv/bin/python -m pytest shared/tests_v2/test_yandex_live.py -q -s
```

CalDAV может вернуть другой адрес созданного ресурса. Сервис проверяет адрес из ответа и при необходимости ищет собственный UID в выбранном календаре. Он сохраняет полученный адрес, нормализованное содержимое и ETag. Яндекс удаляет произвольные `X-` поля: восстановление после потерянного ответа опирается на сохранённое намерение и проверку содержимого, а не на сохранность такого маркера. Повторная активация ранее удалённой встречи получает новый UID.

Живая проверка условных записей: устаревший настоящий ETag в `If-Match` отклоняется с `412`. Однако Яндекс игнорирует `If-None-Match: *` и может заменить существующий ресурс. Поэтому атомарную гарантию «создать только при отсутствии» сервер не предоставляет. Первое создание использует уникальный UID, предварительное чтение и сериализацию в БД. После неоднозначного исхода создания повторная доставка выполняет только чтение и поиск по UID; повторный PUT запрещён. Если подтвердить создание не удалось, ограниченные повторы завершаются ошибкой в core. Ручной технический повтор продолжает безопасную сверку; он не создаёт ресурс заново. Это ограничение провайдера по сравнению с исходным планом.

Описание часового пояса включает историческую базу с 1970 года (или раньше для более старой встречи): Яндекс неверно разбирает определения, начинающиеся только в будущем. Библиотека генерирует переходы; серверная нормализация проверяется отдельно, полный ответ и ETag сохраняются для обнаружения последующих внешних изменений.

## Результаты проверки реализации

Проверено 25 октября 2026 года: 122 backend-теста и 22 frontend-теста проходят; production-сборка frontend, Ruff, разбор YAML и синтаксис build-скриптов проходят. Обычный backend-прогон пропускает 8 opt-in проверок внешних зависимостей, включая live-тест Яндекса. Live-тест Яндекса запущен отдельно и проходит: создание, повторная доставка, перенос, пустые заметки, напоминание, серия через весенний переход DST в Europe/Berlin, отдельное повторение, его отмена, удаление, внешний конфликт и внешнее удаление. Тестовые ресурсы удалены; остальные события не изменялись.

Образ Docker и развёртывание в Kubernetes не выполнялись. Полная проверка с настоящими PostgreSQL/RabbitMQ требует соответствующего тестового окружения; доставка проверена с подменёнными транспортами и транзакционной БД. Для включения интеграции в окружении нужны миграция, сервис и Secret с `YANDEX_TOKEN_KEY`; тестовые credentials в репозиторий не включены.

Живая проверка выявила ограничение Яндекса: экспортируемое время округляется до минуты. Встречи с ненулевыми секундами или микросекундами сохраняются локально, но получают ошибку `calendar_precision_unsupported` вместо отправки с потерей точности. Технический повтор такую ошибку не исправляет; изменение времени до целой минуты создаёт новое задание, которое может продолжить отправку.
